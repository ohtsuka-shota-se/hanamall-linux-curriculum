```
佐藤 Sato  08:45
田中さん、昨夜はほんとにお疲れ様でした！
今後のために、昨夜の障害で出てきた用語を整理しておきますね。

━━━━━━━━━━━━━━━━━━
📦 ストレージの4層構造
━━━━━━━━━━━━━━━━━━

Linuxのストレージは、下から上に向かって4つの層で成り立っています。
マンションに例えるとわかりやすいです。

[層1] 物理ディスク /dev/sda
  → マンション1棟そのもの（HDD / SSD の本体）

[層2] パーティション /dev/sda1, /dev/sda2
  → マンションを「101号室」「102号室」に区切ること
    fdisk コマンドで間仕切り壁を作るイメージ

[層3] ファイルシステム（ext4, xfs など）
  → 部屋の内装・棚の並べ方
    mkfs.ext4 でフォーマット＝「部屋を使えるように整備する」こと
    フォーマット前の部屋は「ただの空間」でOSは読み書きできない

[層4] マウントポイント /var/log, /mnt/data
  → 廊下（OS のディレクトリツリー）と部屋をつなぐドア
    mount コマンドでドアを開けて初めて入れる
    umount でドアを閉じる（ファイルにはアクセスできなくなる）

df は「各部屋の広さと使用状況」を一覧する
du は「その部屋の中で誰がどれだけ場所を取っているか」を調べる

━━━━━━━━━━━━━━━━━━
🏗️ LVM は「壁を壊して部屋を広げる魔法工事」
━━━━━━━━━━━━━━━━━━

普通のパーティション拡張は「入居者を全員退去させてから工事する」
つまりサービスを止める必要がある。

LVM（Logical Volume Manager）は「入居者がいる状態のまま
壁をぶち抜いて部屋を広げられる」仕組みです。

PV（Physical Volume）= 工事に使える「建材の在庫」
VG（Volume Group）  = 複数の建材をまとめた「資材倉庫」
LV（Logical Volume）= 実際にアプリが使う「部屋」

新しいディスクを PV として登録 → VG に追加 → LV を拡張
という順番で「工事中もサービス継続」で容量を増やせます。

━━━━━━━━━━━━━━━━━━
🗑️ rm したのに df が変わらない謎
━━━━━━━━━━━━━━━━━━

昨夜「rm したのにディスクが空かない！」となりましたよね。
これは Linux の設計上の仕組みです。

rm は「ファイルへの名前（看板）」を消すだけです。
データ本体は「参照しているプロセスが 0 になったとき」に初めて消えます。

Apache が access.log を開いたまま rm すると：
  → 看板は消えるが Apache はまだそのファイルに書き続けている
  → ディスクの実体は残り続ける（lsof で "(deleted)" と見える）
  → Apache を再起動して「参照ゼロ」になって初めてディスクが解放される

これを知らないと深夜に「削除したのに空かない！」とパニックになります 😅
昨夜の田中さんがまさにそれでしたね（笑）

疑問があったら何でも聞いてください！
```

## 📚 学習内容

### 1. ディスク容量確認

#### 💡 `df` と `du` の違い
- **`df`（disk free）**：ファイルシステム単位の使用量。マウントポイントごとの全体像が分かる。
- **`du`（disk usage）**：ディレクトリ・ファイル単位の使用量。「どこが使っているか」の特定に使う。

ディスクフルのトラブル対応は「`df` で全体確認 → `du` で原因ディレクトリ特定」の流れ。

```bash
df -h                           # マウント済みファイルシステムの使用量（-h = human readable）
df -h /var                      # 特定パスだけ確認

# ディスクを食っているディレクトリを特定するパターン
du -sh /* 2>/dev/null | sort -rh | head -10
# -s: サブディレクトリを再帰せず合計だけ表示
# -h: 人が読みやすい単位（MB, GB）
# sort -rh: サイズの大きい順

du -sh /var/* 2>/dev/null | sort -rh | head -10  # /varの中を調べる
du -sh /var/log/* 2>/dev/null | sort -rh          # /var/logの中を調べる
```

### 2. パーティションとマウント

#### 💡 ストレージの4層構造（概念図）

```
【物理ディスクからマウントポイントまでの流れ】

 ┌──────────────────────────────────────┐
 │  物理ディスク /dev/sda               │  ← HDD / SSD 本体（マンション1棟）
 │                                      │
 │  ┌────────────┐  ┌────────────┐      │
 │  │ /dev/sda1  │  │ /dev/sda2  │      │  ← パーティション（部屋割り）
 │  │  (100GB)   │  │  (400GB)   │      │     fdisk / parted で作成
 │  └─────┬──────┘  └─────┬──────┘      │
 └────────┼───────────────┼─────────────┘
          │               │
      mkfs.ext4       mkfs.xfs           ← フォーマット（内装・棚の設置）
          │               │
     ┌────▼────┐      ┌───▼────┐
     │  ext4   │      │  xfs   │         ← ファイルシステム（棚の整理方法）
     └────┬────┘      └───┬────┘
          │               │
       mount            mount            ← マウント（廊下とドアをつなぐ）
          │               │
     ┌────▼────┐      ┌───▼────────┐
     │    /    │      │  /var/log  │     ← マウントポイント（入口のドア）
     └─────────┘      └────────────┘

マウント前：ls /var/log しても「空っぽ」に見える
マウント後：ls /var/log で中のファイルが見える
```

#### 💡 パーティション・マウントとは
- **パーティション**：物理ディスクを論理的に分割したもの。`/dev/sda1`, `/dev/sda2` など。
- **ファイルシステム**：パーティションをフォーマットしたもの（ext4, xfs, etc）。OSが読み書きできる形式。
- **マウント**：ファイルシステムをディレクトリツリーの特定の場所（マウントポイント）に接続すること。

Linuxではすべてのストレージはマウントすることでアクセスできるようになる。
USBメモリを挿しても自動でマウントされるのはこの仕組みのおかげ。

```bash
lsblk                          # ブロックデバイス（ディスク）一覧と構造を表示
fdisk -l                       # パーティション詳細

# 新しいディスクにパーティションを作成
sudo fdisk /dev/sdb
# → n（新規）→ p（プライマリ）→ 1（番号）→ Enter（デフォルト）→ w（書き込み）

# フォーマット（ext4が最も一般的）
sudo mkfs.ext4 /dev/sdb1

# マウント（一時的）
sudo mkdir -p /mnt/data
sudo mount /dev/sdb1 /mnt/data

# 永続化：/etc/fstab に追記（再起動後も自動マウントされる）
# UUID で指定するのが推奨（デバイス名は変わることがある）
sudo blkid /dev/sdb1           # UUIDを確認
echo "UUID=xxxx  /mnt/data  ext4  defaults  0  2" | sudo tee -a /etc/fstab
sudo mount -a                  # fstabを再読み込みしてマウント確認
```

> **⚠️ fstab の書き間違いに注意：**
> fstab に誤った設定を書いて再起動すると、サーバーが起動しなくなることがある。
> 必ず `sudo mount -a` で事前にエラーがないか確認してから再起動すること。

### 3. LVM（論理ボリューム管理）

#### 💡 LVMとは何か、なぜ使うのか
従来のパーティション管理では、「ディスクがいっぱいになったら物理的にディスクを交換する」しかなく、
サービスを止める必要があった。LVM（Logical Volume Manager）を使うと：
- 複数の物理ディスクを1つの仮想ディスクとして扱える
- サービスを止めずにオンラインでディスクを拡張できる
- スナップショット（瞬間バックアップ）が取れる

#### 💡 LVMの3層構造（概念図）

```
【LVMの仕組み：物理 → 仮想の変換レイヤー】

  ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ /dev/sdb │   │ /dev/sdc │   │ /dev/sdd │  ← 物理ディスク（建材の在庫）
  └────┬─────┘   └────┬─────┘   └────┬─────┘
       │ pvcreate      │ pvcreate      │ pvcreate
       ▼               ▼               ▼
  ┌────────┐       ┌────────┐     ┌────────┐
  │  PV    │       │  PV    │     │  PV    │   ← Physical Volume
  │ 500GB  │       │ 500GB  │     │ 500GB  │     （LVMに登録した建材）
  └────┬───┘       └───┬────┘     └───┬────┘
       │               │               │
       └───────┬────────┘               │ vgextend（後から追加OK）
               ▼                        │
  ┌────────────────────────────────────▼─┐
  │           VG: ubuntu-vg              │  ← Volume Group
  │           （合計容量: 1.5TB）         │    （資材倉庫 = 使える容量の貯水池）
  └──────────────────┬───────────────────┘
                     │ lvcreate / lvextend
                     ▼
        ┌────────────────────────┐
        │  LV: ubuntu-lv         │          ← Logical Volume
        │  （アプリが実際に使う） │            （アプリから見える「部屋」）
        └────────────┬───────────┘
                     │ mkfs.ext4 / resize2fs
                     ▼
        ┌────────────────────────┐
        │  ファイルシステム (/)   │          ← OSが読み書きする領域
        └────────────────────────┘

【拡張の手順イメージ】
  新ディスク追加 → pvcreate → vgextend → lvextend → resize2fs
  ↑ここまでサービス無停止で実行可能！
```

```bash
# LVM構成確認
pvs   # Physical Volume（物理ディスクの登録状況）
vgs   # Volume Group（VGの空き容量）
lvs   # Logical Volume（実際に使うボリューム一覧）

# 容量拡張の手順
sudo pvcreate /dev/sdc                            # 新ディスクをPVに登録
sudo vgextend ubuntu-vg /dev/sdc                  # VGに追加
sudo lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv  # LVを拡張
sudo resize2fs /dev/ubuntu-vg/ubuntu-lv           # ファイルシステムをリサイズ

# 確認
df -h /    # ルートの容量が増えたことを確認
```

### 4. rsync によるバックアップ

#### 💡 rsyncとcpの違い
`cp` は毎回すべてをコピーするが、`rsync` は「差分だけ同期する」ため高速。
`--delete` を付けると転送元で削除したファイルを転送先でも削除できる。
SSHを経由してリモートサーバーへのバックアップにも使える。

```bash
rsync -av --delete /var/www/ /backup/www/
# -a: アーカイブモード（パーミッション・タイムスタンプを保持）
# -v: 詳細表示
# --delete: 転送元にないファイルを転送先でも削除

# dry-run：実際には何もしない（実行前の確認に必須）
rsync -av --dry-run --delete /var/www/ /backup/www/

# SSH経由でリモートサーバーへ
rsync -avz -e ssh /var/www/ ubuntu@backup-server:/backup/www/
# -z: 転送時に圧縮（ネットワークが遅い環境で有効）
```

### 5. 削除してもディスクが空かない問題と lsof

#### 💡 「削除したのに df が変わらない」とき

```
【rm してもディスクが解放されない仕組み】

  ファイルシステム内部のイメージ：

  ディレクトリエントリ（名前の台帳）
  ┌─────────────────────────────────────┐
  │ access.log  → inode #4521          │  ← rm するとここだけ消える（看板撤去）
  │ error.log   → inode #4522          │
  └─────────────────────────────────────┘
                          │
                          ▼
  inode（ファイルの実体情報）
  ┌─────────────────────────────────────┐
  │ inode #4521                         │
  │   参照カウント: 1（apache2が開いてる）│  ← rm 後も 0 にならないので残る
  │   データブロック: [block 1000-1200] │
  └─────────────────────────────────────┘

  rm access.log 実行後：
    名前（台帳のエントリ）は消えた
    inode の参照カウントはまだ 1（apache2 が fd で参照中）
    → ディスクの実体は解放されない！

  apache2 再起動後：
    apache2 がファイルディスクリプタを閉じる
    参照カウントが 0 になる
    → ディスクの実体が解放される ✅
```

ファイルを `rm` で削除しても `df` の使用量が減らないことがある。
これは **「プロセスがファイルを開いたまま（オープン中）」** のとき。

```bash
# lsof（list open files）：どのプロセスがどのファイルを開いているか確認
sudo lsof | grep deleted          # 削除済みだがまだ開かれているファイルを探す

# 具体例：Apache がログを開いたまま、ログファイルを rm してしまった場合
sudo rm /var/log/apache2/access.log
df -h /var/log    # → 容量が減らない！

sudo lsof | grep "access.log"
# apache2  1234  www-data  5w  REG  ... /var/log/apache2/access.log (deleted)
# → apache2 (PID:1234) がまだ開いている

# 解決方法1：Apache を再起動してファイルを閉じさせる
sudo systemctl restart apache2
df -h /var/log    # → 今度は減る

# 解決方法2：ファイルを削除せず中身だけ空にする（ログローテーションの考え方）
> /var/log/apache2/access.log   # ファイルは残したまま中身を空にする
```
